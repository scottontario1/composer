## Recommendation and compatible grafts

Use A's paired-document workspace as the current-scope base: one shell, one document owner, two independent editors, integrated linked cards, and copied self-contained recipes. It meets the combination/mobile brief with fewer product concepts than B. Retain A's explicit self-contained recipe boundary and migration adoption protection.

Graft B's distinction between structural validity and execution readiness. Users must be able to save/repair an unfinished workflow while prompt generation remains blocked. Graft its immutable prompt preview with visible invalidation after edits, preservation of form text through responsive changes, software-keyboard acceptance checks, and causal-analysis caching by semantic changes rather than layout. These features strengthen existing boundaries without requiring multiple documents.

Consider B's staging/read-back recovery as a later persistence hardening decision after storage bounds are measured. Preserve its honest failure and non-atomicity descriptions. Do not make multi-document selection, recipe update comparison/replacement, external boundary ports, or a union diagram prerequisites for the initial scope. They are viable extensions, but unsupported complexity for this brief. Keep C's simple shell-owned transfer request/result contract as an implementation interface example. Defer persistent detected-cycle references: recomputed cycle identity and stale-reference recovery add another lifecycle with little demonstrated need.

## Required corrections and uncovered requirements

1. **A's store contract needs an explicit structural/readiness split.** It rejects unsafe outputs in validation while also saying unsupported executable semantics remain repairable. Define which drafts can commit/save and which errors only block compilation. Recipe insertion must guarantee structural safety and avoid introducing unresolved output conflicts, while ordinary editing can preserve incomplete text.
2. **Complete A's schema contract.** Prose increments document revision and uses stored revision for conflict checks, but `Workspace` declares no revision. `SkillOptions` is undeclared. Specify revision and owner/session metadata, opaque unknown-option storage, ordinal initialization and duplicate/missing ordinal handling, layout defaults, and schema adapters. These are design closure tasks, not grounds to add a framework.
3. **Make legacy export ordering policy explicit.** All candidates want stable authored order independent of layout, while v1 exports lack that field and older HTML sorts by y/x/id. A and B correctly initialize migration from the old topological result; C incorrectly chooses node-array order. For subsequent v1 exports, declare whether layout is preserved with a visible ordering-loss warning or compatibility coordinates are synthesized with an explicit layout-loss warning. Full-workspace export must preserve both. Do not promise exact legacy behavior and exact layout preservation simultaneously after authored order diverges.
4. **Set bounded full-workspace/recipe transfer limits before implementation.** A leaves its aggregate byte cap undecided; B's 1MB conservative cap has no complete aggregate policy. Bound recipes, reference count, notes, and combined documents so valid legacy maxima have a known transfer/recovery path. The brief asks contracts and failure behavior, so this remains unfinished design detail.
5. **C fails mandatory composite coverage.** It gives no composite assumption, recipe/subworkflow contract, caller flow, migration treatment, or verification proposal. Its loop-reference feature is prose-only in a schema supporting only variable endpoints. These omissions prevent choosing C as a complete base.

All candidates preserve offline standalone delivery, seven canonical skills, independent views, outside-browser prompt execution, and DAG-versus-causal distinction. Verification remains proposed; no design establishes mobile browser/file-storage usability or deeper canonical skill correctness.

Do not claim universal-graph versus shell or recursive-composition alternatives were evaluated. Models were inherited; model-family diversity is unverified and is not inferred from candidate labels.
